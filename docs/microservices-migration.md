# Перенос данных монолита

Свежая установка применяет `migrate --service identity|workspace|environments up`
по отдельности от владельцев схем. Перенос существующей базы выполняется
изолированной командой `migrate transfer-monolith` с временной ролью,
способной перемещать исходные объекты и назначать владельцев. Application
roles этих полномочий не получают.

Проверьте перенос сначала на копии PostgreSQL и данных восстановления
Redis. Остановите приём новых работ и выдачу новых provisioning lease.
Сохранённую очередь исполнений нужно завершить на прежнем kernel. Если
исход уже отправленной команды достоверно неизвестен, сохраните
`UNKNOWN` и не отправляйте её повторно. Сохраните журнал и checkpoints.
Остановите монолит, его workers и дочерние Ansible/SSH процессы и
отключите автоматический рестарт.

Сверьте незавершённые provider operations с состоянием Selectel и
инвентарём ресурсов. Истёкшая lease не подтверждает завершение уже
принятого облаком запроса. Для работающих сессий подготовьте gRPC-агент
и сертификат выделенной VPS, сохранив SQLite journal, workspace,
checkpoints и session UUID. Новый kernel получит новое поколение.
Python-переменные в памяти прежнего kernel после замены недоступны.
Нельзя выдавать новый runtime-агент за готовый, пока он не прошёл mTLS
проверку с удостоверением Environments.

Подготовьте JSON инвентарь с `version: 1` и `source_schema: "public"`.
Поля `admission_stopped`, `queue_drained`, `processes_stopped`,
`automation_stopped`, `cloud_reconciled` и `backup_verified` фиксируют
результат этих внешних проверок. В `roles` задайте каждому сервису
`owner` и `app`. Укажите известные `cloud_actions` с `operation_id` и
`outcome` (`completed` или `cancelled`). Для VPS пула в состояниях
`PREPARING` и `DELETING` в качестве `operation_id` используется ID
записи пула. Для каждого такого действия укажите фактические `server_id`,
`volume_id` и `port_id` для оставшихся ресурсов. Перед переносом сверьте
их с сохранёнными полями исходной записи. При расхождении перенос
останавливается до завершения сверки. В `agents` перечислите
назначенные VPS с `host_id`, `version`, `grpc_ready` и
`state_preserved`. Credentials в инвентарь не входят.

```sh
migrate transfer-monolith --dry-run --inventory-file cutover.json
migrate transfer-monolith --apply --inventory-file cutover.json
```

Dry run проверяет известную исходную версию, доступность блокировок,
завершение очереди, lease и внешний инвентарь. Для `--apply` целевые
схемы могут существовать, но должны быть пустыми. Команда меняет схемы
таблиц в одной транзакции вместе с индексами и связанными
последовательностями, снимает межсервисные FK на users, записывает
histories и права. Старые refresh rows сохраняются в Identity для архива.
Действующие Redis сессии и ключи токенов сохраняются отдельно.
При потерянном ответе повторите вызов с тем же инвентарём. Известный
checkpoint вернёт сохранённый отчёт.

Перед допуском пользователей сверьте counts и ревизии документов, ACL,
авторство, очереди, lease, active user guards и доступность агентов.
Первый запуск Go-сервисов выполните с `WORKERS_PAUSED=true` при закрытом
внешнем admission. Проверьте состояние БД, health, mTLS и агентов.
Затем перезапустите сервисы с `WORKERS_PAUSED=false` при закрытом
admission, чтобы запустить recovery. Подтвердите фактическое состояние
ресурсов и завершение cleanup, после чего откройте BFF.
План переключения и восстановления production
проверяются в [infra#163](https://github.com/Cringe-Driven-Development-Team/infra/issues/163).
