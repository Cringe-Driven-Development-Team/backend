# Логирование backend с привязкой к запросу

Дата: 19.10.2026. Задача: [backend#19](https://github.com/Cringe-Driven-Development-Team/backend/issues/19).
Код: `Cringe-Driven-Development-Team/backend`. Этот документ фиксирует согласованное
поведение; порядок реализации будет в отдельном плане.

## Цель и результат

Когда запрос завершается ошибкой, разработчик находит по `request_id` маршрут,
прикладное действие, операцию хранилища и безопасную причину сбоя. Значимые
успешные действия тоже видны в логах. Уровень подробности можно изменить без
пересборки приложения. Логи не содержат пароли, токены, cookie, SQL-параметры,
тела запросов и содержимое блокнотов.

Логи предназначены для команды, которая разбирает сбои Go API через вывод
контейнера и CI/CD. Существующий JSON-формат `slog` сохраняется; записи получают
стабильные названия событий и поля, пригодные для поиска.

## Согласованный объём

Логирование охватывает запуск, HTTP-конвейер, usecase пользователя и блокнотов,
PostgreSQL-адаптеры и обращения к S3. Не требуется записывать каждый внутренний
шаг функции: действие представляется одним событием с исходом. Одна и та же
неожиданная ошибка не печатается дословно на каждом слое.

| Уровень | События |
| --- | --- |
| `Debug` | Чтения и операции PostgreSQL/S3: название, длительность, исход |
| `Info` | Итог HTTP-запроса и значимые успешные изменения: регистрация, вход, обновление и завершение сессии, создание блокнота, добавление и удаление ячейки |
| `Warn` | Ожидаемые отклонения, после которых запрос или процесс продолжает работу; обычный неверный пароль не является предупреждением |
| `Error` | Неожиданный сбой запроса или запуска, с безопасным кодом причины |

`log/slog` не имеет уровня `Fatal`: критическая ошибка запуска записывается на
`Error`, затем процесс завершается с ненулевым кодом. Успешные чтения остаются
на `Debug`, чтобы обычный `Info` не создавал запись на каждый запрос к хранилищу.

## Передача контекста и поля

Нейтральный к HTTP пакет наблюдаемости предоставляет операцию помещения
`request_id` в `context.Context` и чтения из него. HTTP middleware создаёт ID
до остальных проверок и возвращает его в `X-Request-ID`. Общий `slog.Handler`
добавляет ID к любой записи `slog.*Context`, сделанной с этим контекстом.
Usecase и адаптеры продолжают передавать полученный `ctx`; они не импортируют
HTTP-пакеты. Записи запуска приложения без запроса не получают фиктивный ID.

Входящий `X-Request-ID` допускается только в ограниченном безопасном формате и
размере; для пустого или некорректного значения создаётся новый UUID. Это
предотвращает попадание произвольного текста заголовка в лог и ответ. Итоговая
запись HTTP содержит `request_id`, метод, шаблон маршрута либо `unmatched`,
статус и длительность. Шаблон маршрута передаётся из маршрутизатора в общие
данные запроса: внешняя обёртка не может надёжно прочитать его из исходного
`http.Request`.
Обёртка `ResponseWriter` должна сохранять необходимые
интерфейсы стандартного сервера, чтобы не ломать streaming/flush; если код ответа
не записан явно, итогом считается 200. Для panic и ранних отказов запись тоже
создаётся ровно один раз.

События usecase имеют стабильные имена вида `user.login`, `session.refresh`,
`notebook.create`, `notebook.cell_create`, `notebook.cell_delete` и поле `outcome`.
Каждое успешное изменение даёт одну запись `Info` на уровне usecase плюс
итоговую запись HTTP. Для операций PostgreSQL/S3 используются названия методов вроде `user.create` и
`notebook.put`, `duration` и `outcome`. Операция `QueryRow` считается завершённой
после `Scan`, чтобы в длительность и исход вошла ошибка чтения результата.
Идентификаторы внутреннего пользователя и блокнота допускаются при наличии,
но логин, имя блокнота и текст ячейки не записываются.

`LOG_LEVEL` принимает `debug`, `info`, `warn`, `error`; значение по умолчанию —
`info`. Неизвестное значение отклоняется при запуске с понятной ошибкой.
Окружение читается тем же механизмом, что остальные настройки. Формат вывода
не меняется в рамках этой задачи.

## Ошибки и чувствительные данные

Ошибка несёт два разных представления: исходная Go-ошибка остаётся в цепочке
возвратов и HTTP-ответах по действующим правилам, а лог получает только
разрешённые поля. На уровне адаптера допустимы название операции, категория
ошибки и код PostgreSQL (`SQLSTATE`) без `Detail`, SQL-текста и аргументов.
Точка входа при сбое запуска и внутренний HTTP-обработчик не печатают
произвольный `err.Error()`: оба записывают безопасный код/категорию ошибки,
а HTTP-обработчик также `request_id`. Статические
ошибки криптографической проверки можно различать по типу/коду, сохраняя
диагностику сбоя без хеша и пароля. Ожидаемые 4xx, включая неверный пароль,
не создают запись `Error`.

Не логируются полный URL с query, заголовки, тело, cookie, пароль, access или
refresh-токен, их хеши, SQL-параметры, содержимое `.ipynb` и секреты S3.
Тесты используют заметные значения-сентинелы для проверки отсутствия утечек.
Успешное логирование не меняет HTTP-коды, тела ответов, cookie и семантику
операций БД/S3.

## Приёмка

1. Для одного запроса `request_id` совпадает в HTTP, usecase и логах операции
   хранилища; ответ содержит тот же `X-Request-ID`. Это верно и для 401/403,
   404/405, 500 и panic, где слой фактически вызван.
2. Итог HTTP-запроса содержит правильный статус, метод, безопасный маршрут и
   длительность. Успешное изменение получает одно событие `Info`; чтение и
   обращение к БД/S3 видно на `Debug`.
3. На `Info` записи `Debug` отсутствуют; при `LOG_LEVEL=debug` появляются.
   Неверное значение `LOG_LEVEL` не запускает сервер.
4. Ошибка БД позволяет увидеть название операции и SQLSTATE, если он доступен.
   Неверный пароль не попадает в `Error`, а сбой проверки пароля остаётся
   отличимым от несовпадения.
5. Ни один из секретных сентинелов не встречается в проверяемых логах, включая
   случаи ошибки и некорректного входящего `X-Request-ID`.
6. `go test -race ./...`, `make check` и `make docker-build` проходят;
   документация окружения и логирования соответствует реализации.

## Не входит

Централизованный сбор логов, трассировка между сервисами, изменение HTTP API,
запись всех SQL-запросов, аудит действий пользователей и новые внешние
зависимости для логирования.
