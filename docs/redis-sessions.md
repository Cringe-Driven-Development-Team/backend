# Redis: переключение, восстановление и откат

## Подключение

API читает `REDIS_HOST` (по умолчанию `redis`), `REDIS_PORT` (`6379`),
`REDIS_PASSWORD` и `REDIS_DB` (`0`). Порт должен быть 1–65535, DB — неотрицательным,
host — непустым. Пустой пароль допускается для отдельного тестового Redis;
локальный Compose задаёт собственный пароль, production получает пароль из Vault.
Секреты, токены и содержимое auth-записей в логи не выводятся.

`REDIS_DIAL_TIMEOUT=2s` ограничивает соединение, `REDIS_OPERATION_TIMEOUT=1s` —
операцию, чтение/запись и ожидание пула. Настройки проверяются при старте;
ошибочные или неположительные Redis-таймауты запрещают запуск. Более ранний
deadline запроса сохраняется. Команды Redis не повторяются (`MaxRetries=-1`).
При старте выполняется PING; Redis-клиент закрывается при ошибках запуска,
SIGINT/SIGTERM и завершении API. Graceful shutdown HTTP ограничен 10 секундами.

Подключаться нужно к авторитетному primary, не к read replica и не к балансировщику
реплик. Каждый защищённый запрос зависит от Redis: сбой даёт 500, без локального
положительного кеша и fallback. `noeviction` при исчерпании памяти приводит к ошибке
записи, а не к вытеснению произвольных сессий.

## Переключение PostgreSQL → Redis

1. Проверить, что infra#46 / PR #65 влиты **и выкачены через deploy-backend.yml**;
   одного site.yml недостаточно. Проверить PONG из сети `app` и REDIS_* API.
2. Остановить все экземпляры старого API. Пользователей и блокноты сохранить.
3. Очистить `refresh_sessions` в PostgreSQL (`DELETE FROM refresh_sessions;`).
   Новая миграция `20261030120000` также выполняет эту очистку при первом старте.
   Таблица остаётся до отдельной последующей миграции; старые миграции не менять.
4. Запустить новый API с Redis и новыми обязательными claims. Старые сессии не
   переносить, JWT без sid/версии не поддерживать. Потребуется повторный вход.
5. Через BFF проверить login/register, refresh, logout и защищённые ручки.
   Сохранить ещё не истёкший access, выполнить logout и убедиться в 401 с этим
   access на новом запросе, в том числе к другому экземпляру API. Проверить,
   что другое устройство осталось авторизованным.

Production Redis уже принадлежит infra: сервис `redis`, сеть `app`, без внешнего
порта; `REDIS_HOST=redis`, `REDIS_PORT=6379`, `REDIS_DB=0`. Не создавать второй
production Redis. Локальный Compose имеет отдельный volume и локальный пароль.

## Потеря данных и восстановление старой копии

Полная потеря Redis отзывает существующие access/refresh: отсутствие auth-записи
или версии не разрешает вход по одной подписи. Повторный login создаёт новую
случайную начальную версию. Не удалять только версии при сохранённых сессиях.
Обычный перезапуск с актуальным AOF сохраняет версии, активные сессии и отзыв.

AOF `appendfsync everysec` может потерять последние подтверждённые изменения при
аварии, включая logout/RevokeAll. Атомарность Lua не обеспечивает сохранение
отзыва при rollback данных. Дополнительного механизма гарантированного отзыва
после аварийного отката в этой реализации нет.

Восстановление старого snapshot/AOF может вернуть отозванную сессию. При любом
**обнаруженном** восстановлении устаревшего состояния:

1. Закрыть auth-трафик и остановить **все** экземпляры API.
2. Восстановить Redis и проверить, что используется нужная DB и primary.
3. Запустить `scripts/reset-auth-sessions.sh` с `AUTH_API_STOPPED=yes`. Скрипт
   очищает через SCAN/DEL `auth_session:*`, `refresh_session:*` и
   `user_session_version:*`, затем проверяет отсутствие ключей. Он не использует
   FLUSHDB и не затрагивает другие семейства ключей.
4. При ошибке оставить API остановленным. Повторная очистка безопасна.
5. После успешной очистки запустить API, проверить отказ старых access/refresh
   и успешный новый login; затем открыть auth-трафик. Всем нужен повторный вход.

Для локального Compose (после `docker compose stop api`):

```bash
docker compose exec -T -e AUTH_API_STOPPED=yes -e REDIS_HOST=redis \
  redis sh -s < scripts/reset-auth-sessions.sh
```

В production использовать Compose в `/opt/cellestial` и проверенную копию скрипта.
Пароль предварительно передаётся оператором через окружение из approved infra/Vault
workflow, без вывода или значения в аргументах команды:

```bash
docker compose exec -T -e AUTH_API_STOPPED=yes -e REDIS_HOST=redis \
  -e REDIS_PORT=6379 -e REDIS_DB=0 -e REDIS_PASSWORD \
  redis sh -s < /trusted/backend/scripts/reset-auth-sessions.sh
```

Для изолированных тестов скрипт поддерживает `AUTH_REDIS_NAMESPACE`; в production
он пустой. `REDIS_DB` должен совпадать с конфигурацией API.

## Откат

Остановить новый API. Redis-сессии обратно в PostgreSQL не импортировать.
Старый stateless middleware может принять прежние JWT, поэтому очистки refresh
недостаточно: согласованно сменить ключ выпуска/проверки JWT и удалить старый
verification key из доверенных. Только затем запустить старый образ и проверить
отказ сохранённых access JWT. Не применять Down для восстановления credentials.
Пользователям потребуется повторный вход; конфигурация и выкатка выполняются в infra.

## Проверки

`REDIS_TEST_ADDR=host:port make redis-test` запускает реальные Redis-тесты с race.
`REDIS_TEST_PASSWORD` задаёт тестовый пароль. Без адреса обычные unit-тесты
пропускают интеграцию; с явно заданным недоступным адресом она завершается ошибкой.
Каждый тест использует случайный namespace и очищает только свои записи.

Для полного прогона: задать `REDIS_TEST_ADDR`, `REDIS_RECOVERY_TESTS=1` и выполнить
`make check`. Нужны Docker и redis-cli в PATH. Restart-тест запускает отдельный
Redis 8 с AOF и volume; тест старой копии использует реальный RDB DUMP/RESTORE
и исполняет скрипт очистки. Вместо Docker локально можно задать `REDIS_SERVER_BIN`
путём к redis-server. CI запускает эти проверки в обязательном job `test`,
основные интеграционные тесты обращаются к отдельному service Redis 8.
