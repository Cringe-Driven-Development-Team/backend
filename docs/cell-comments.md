# Комментарии к ячейкам

Go API хранит плоскую стену каждой ячейки отдельно от ipynb и результатов исполнения.
Пути ниже относительны `/api/v1`; полный контракт — [spec/openapi.json](../spec/openapi.json).
Все запросы требуют `X-BFF-Key`. Действующий Bearer и сессия требуются для всех операций.

## Доступ

Чтение следует [текущим правам блокнота](notebook-sharing.md). Посетитель только
по ссылке получает 404 при запросе комментариев по ID блокнота. Авторство привязано к ID пользователя, смена логина
сохраняет права. GET, POST и PATCH возвращают текущий логин и `author.avatar_url`
из профиля Identity. Ссылка совпадает с `GET /users/me`, а без аватара поле равно
`null`. После смены аватара новый URL появляется и у ранее созданных комментариев.

| Посетитель с текущим доступом | Читать | Создать | Изменить свой | Изменить чужой | Удалить свой | Удалить чужой |
|---|---|---|---|---|---|---|
| Владелец | Да | Да | Да | Нет | Да | Да |
| viewer | Да | Нет | Нет | Нет | Нет | Нет |
| commenter | Да | Да | Да | Нет | Да | Нет |

Отзыв доступа закрывает все операции стены. Смена роли на `viewer` закрывает запись, включая правку и удаление собственных сообщений. Сообщения сохраняются. Доступ и запись проверяются
в одной транзакции с блокировкой блокнота, общей с изменением шэринга и удалением.

## Счётчики

`GET /notebooks` возвращает `comments_count` для каждого блокнота страницы.
`GET /notebooks/{id}` возвращает этот же итог и `cell_comments_count` с числом
сообщений по ID ячеек. У блокнота без комментариев значения равны `0` и `{}`.
Ячейки без сообщений отсутствуют в объекте. Счётчики учитывают все страницы
обсуждений, включая ответы, и отражают добавление и удаление сообщений.
Редактирование текста количество сообщений не меняет.

## Операции

`WALL_URL` в примерах — `$API_URL/api/v1/notebooks/<id>/content/cells/<cell_id>/comments`.
Значения BFF_API_KEY и ACCESS_TOKEN — локальные переменные, не параметры браузера.

```bash
# Первая страница.
curl --get "$WALL_URL" \
  -H "X-BFF-Key: $BFF_API_KEY" -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data-urlencode 'limit=20'

# Создание: 201 с полным DTO.
curl "$WALL_URL" -X POST \
  -H "X-BFF-Key: $BFF_API_KEY" -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' --data '{"text":"Комментарий\nк ячейке"}'

# Изменение своего: 200 с полным DTO и новой датой.
curl "$WALL_URL/$COMMENT_ID" -X PATCH \
  -H "X-BFF-Key: $BFF_API_KEY" -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' --data '{"text":"Обновлённый комментарий"}'

# Физическое удаление: 204 без тела; повтор — 404.
curl "$WALL_URL/$COMMENT_ID" -X DELETE \
  -H "X-BFF-Key: $BFF_API_KEY" -H "Authorization: Bearer $ACCESS_TOKEN"
```

POST/PATCH принимают только обязательное строковое поле `text`, с точным регистром
имени. Внешние Unicode-пробелы удаляются, после этого допустимы 1–5000 Unicode
code points. Внутренние пробелы и переводы строк сохраняются. null, NUL,
некорректный UTF-8, лишние поля и второй JSON-объект отвергаются. Общий предел
сырого тела — 512 KiB. HTML-подобный текст возвращается как данные и должен
отображаться интерфейсом с экранированием, без вставки в HTML.

DTO содержит `id`, `notebook_id`, `cell_id`, `author: {id, login}`, `text`,
`created_at`, `updated_at`, `can_edit`, `can_delete`. Секреты и дополнительные
данные профиля автора не возвращаются. Флаги вычислены для текущего посетителя;
сервер повторно проверяет права при каждой операции.

Даты имеют формат RFC 3339 в UTC с точностью PostgreSQL до микросекунд, например
`2026-11-22T12:00:00.123456Z`. При создании даты равны. Каждый успешный PATCH,
в том числе с тем же текстом, строго увеличивает updated_at минимум на микросекунду.
created_at не меняется; конкурентные PATCH применяются в порядке успешной записи.

## Страницы

GET возвращает `{items: Comment[], next_cursor: string | null}`. Пустая стена —
`items: []`, `next_cursor: null`. limit по умолчанию 20, диапазон 1–100.
Следующая страница получается передачей next_cursor без изменений:

```bash
curl --get "$WALL_URL" \
  -H "X-BFF-Key: $BFF_API_KEY" -H "Authorization: Bearer $ACCESS_TOKEN" -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data-urlencode 'limit=20' --data-urlencode "cursor=$NEXT_CURSOR"
```

Порядок — created_at DESC, id DESC. Редактирование не перемещает запись.
Курсор подписан и привязан к блокноту и ячейке; размер страницы можно менять.
Удаление граничной записи не ломает курсор. Продолжение страницы идёт к старым
сообщениям, новые получают новым запросом первой страницы. Для неизменной стены
обход полный и без дублей. `next_cursor: null` завершает обход, включая полную
последнюю страницу. Каждый запрос проверяет актуальный доступ.

## Ошибки и независимость от документа

| HTTP | code | Причина |
|---|---|---|
| 400 | validation_error | Неверные ID, text, limit, пустой/повреждённый курсор или курсор другой стены |
| 401 | unauthorized | Запись без сессии или переданный недействительный Bearer |
| 403 | s2s_forbidden | Отсутствующий, неверный или повторный X-BFF-Key |
| 403 | forbidden | Чужой текст при PATCH или чужое сообщение при DELETE без права модерации |
| 404 | not_found | Закрытый/отсутствующий блокнот, ячейка или комментарий не из этой стены |
| 413 | validation_error | Сырое тело больше 512 KiB |
| 500 | internal | Внутренняя ошибка без SQL, текста и секретов |

Порядок проверки — S2S, требуемая сессия, валидация, текущий доступ и привязка,
затем авторство. Все ответы, включая ошибки и 204, содержат Cache-Control: no-store.
Операции не требуют If-Match и сохраняют hash/ETag, source, outputs, даты блокнота
и runtime. Перемещение и изменение source сохраняют стену. Удаление ячейки,
блокнота или физическое удаление автора каскадно удаляют соответствующие комментарии.
Клонирование создаёт блокнот с пустыми обсуждениями.

## Подключение BFF и клиента

Operation IDs: `listCellComments`, `createCellComment`, `updateCellComment`,
`deleteCellComment`. Frontend закрепляет контракт по полному SHA backend вместе
с обычным набором файлов из [правил OpenAPI](openapi.md). SHA выбирают после
публикации изменения; локальный файл не означает существования опубликованного pin.

При отсутствии браузерной сессии BFF не отправляет Authorization. Интерфейс
привязывает страницы к выбранной ячейке, показывает текущий login и дату изменения,
использует can_edit/can_delete, обрабатывает 401/403/404 и безопасно выводит text.
Совместный сценарий включает создание, несколько страниц, изменение/удаление,
чтение с ролью viewer и отзыв доступа с уже открытой стеной.
